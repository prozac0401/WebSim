## Reproducible session

1. First run when the changed feature has playable stages; repeat after the entire current catalog is integrated. Retain original levels 1–3 as early regression coverage. Run `node tests/routine-bot.browser.cjs early` or `node tests/routine-bot.browser.cjs final` for reproducible control coverage, then perform exploratory rendered play for the observations below. Browser evidence goes in `output/playwright/routine-bot/<phase>/`; record exact viewport, touch setting, reduced-motion setting, browser version, screenshots, console/page errors, and actions in a JSON or text report.
2. Use desktop at 1440×900, narrow portrait at 320×740, and ordinary mobile portrait at 390×844 with touch emulation. Insert blocks with clicks/taps, select and move/delete them, undo, enter/leave repeat and condition branches, change function scope, and execute using visible buttons. Test keyboard controls on desktop. Scroll as a player would; inspect whether the map, active instruction, and core execution controls remain understandable on narrow screens. A responsive screenshot alone is not a touch playtest.
3. On a fresh save, determine the goal and first action without reading a long help panel. Solve 1–3. Intentionally hit a wall, identify the highlighted location and command, edit the program without losing it, and retry. Use pause, step, reset, speed, and a next-level transition. Reopen the game and verify that progress and programs survive.
4. In final phase, play a repetition level, a condition level with both outcomes, and a function level. Observe whether the concept reduces repeated editing, the current nested scope is clear, and function entry/return connects to the active block and robot. Solve the multiple-map challenge using the same program. Verify the current catalog's final clear screen, declared prerequisite unlocks, and preserved access to completed original IDs 1–15; distinguish a seeded late-level session from an end-to-end progression session.
5. For each issue, record **observation → problem → concrete change → repeat the same scene** in `routine_bot/PLAYTEST.md`. Name the level, viewport, input actions, and before/after evidence paths. Preserve unresolved issues and mark blocked coverage FAIL or NOT RUN. Re-run the automated suite when the fix affects controls or cancellation.

When editing the inline command tree, run `node tests/routine-bot-tree.browser.cjs` for focused rendered regression evidence in `output/playwright/routine-bot/tree/`. Then inspect the resulting desktop and portrait captures: surrounding commands should remain readable while repeat/condition descendants are expanded. Collapse an ancestor while its descendant is the insertion target, then add a block and verify it lands visibly in the parent. Confirm fold/unfold and choosing a branch are separate actions, each condition branch can fold independently, repeat counts remain editable after a rejected operation, and keyboard focus survives those actions. This fixture-assisted replay is separate from blind exploration and actual human feedback.

For swipe/drag editing, also run `node tests/routine-bot-swipe.browser.cjs` with fresh evidence. Use real pointer sequences (mouse down/move/up and browser touch input), not injected DOM events. Try both swipe directions, short/vertical gestures, protected repeat/fold controls, nested and parent deletion, undo/reload, and an over-budget repair ending in actual success. Use the visible grip to move into/out of repeats and branches, including folded repeats and existing sibling positions; try a self/descendant target. Independently inspect the drag destination feedback, scrolling, and discoverability at both phone widths. Record hardware NOT RUN separately.

For hard command limits, run `node tests/routine-bot-budgets.browser.cjs` and inspect `output/playwright/routine-bot/budgets/migration/`. Observe whether the stored count and required cap are understandable, rejection explains how to proceed, and the repetition level encourages grouping without requiring extra flat commands. Treat the injected old save as a migration fixture, not an authored play solution: the player actions must retain it, delete one block at a time while still over budget, undo/reload safely, and then solve through real execution under the cap. Test desktop and both touch widths. Record this source-informed replay separately from any fresh-save, no-answer exploration.

For timed-hazard changes, run `node tests/routine-bot-hazards.browser.cjs` and inspect `output/playwright/routine-bot/hazards/focused/`. First try the staircase without waiting, observe the highlighted cell/block and time, then preserve its repeat and insert/reorder a wait through visible controls. Test staying on an initially safe tile until a turn or wait makes it dangerous. Read current × versus next ! and expand the timetable on both portrait widths; ensure the robot, marker, time and controls remain usable. After a 4× movement finishes, change to 0.5× and verify the robot and hazard phase do not visually rewind. Check marker recognition during waiting and one unchanged function across differently timed maps. Record observation → problem → fix → same-scene retest, separating old-route replay from novel exploratory play and from source-informed scripted regression. Fixtures may unlock access but must never supply the successful program or runner state.

## Cooperative expansion acceptance

Read the current ordered catalog through the player level selector, not an assumed 15-level sequence. Use the feature-integration early/final phases. Record shared-code branch differences, selection of each robot and its active command, blocked push versus successful push, whole-turn stepping, goal marks under occupied cells, and completion only with all homes/targets satisfied.

Test challenge start, editing/thinking time, run pause, failed retry, help/tutorial exclusion, rest locking, reload continuity, hint marking and success metrics. Help must preserve execution state and closing must not silently run it. A short tutorial rule should link to its actual introduction stage rather than force a duplicate exercise. On 320×740 and 390×844, tap all relevant controls and check that the stage does not cover the editor or dialog.

Keep observation → issue → fix → repeat-scene evidence for each finding. Explicitly report desktop, mobile touch emulation, real Android and real iOS independently (hardware is NOT RUN unless used). Agent/automated play is not a human fun study.

## What to judge

Watch for unclear direction/goal, unexplained collision, invisible active instruction, nested editing without a way back, controls obscured by scrolling, tiny tap targets, unexplained difficulty jumps, repetitive insertion, slow retries, excessive explanation, weak success response, and effects that ignore reduced motion. Identify concrete scenes rather than giving a blanket “fun” score.

Report desktop and touch emulation separately. Mark real Android hardware **NOT RUN** unless an actual Android device was used. Automated and agent exploratory sessions provide observed interaction evidence and design judgments; actual human enjoyment, comprehension, and satisfaction remain unverified without a real user study. Do not turn scripted browser success into a claim of human usability validation.
